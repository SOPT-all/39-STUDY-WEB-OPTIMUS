01 · 문제

이런 적 있지 않나요?

🙈

PR 올라온 걸 몰라요

GitHub 알림은 메일함에 묻히고, 결국 "PR 올렸어요~" 를 디스코드에 직접 써야 해요.

⏰

리뷰어인 걸 몰라요

리뷰어로 지정돼도 본인은 모르고, 리뷰는 하루 이틀씩 밀려요.

🔍

상태 확인이 번거로워요

머지됐는지, 수정 커밋이 올라왔는지 매번 GitHub 에 들어가서 확인해야 해요.

02 · 해결

PR 하나 = 디스코드 스레드 하나

  • PR 을 열면 채널에 PR 카드가 올라가고, 그 카드에 전용 스레드가 생겨요.
  • 이후 리뷰 요청 · 커밋 · 머지 소식은 전부 그 스레드에 쌓여요.
  • 채널은 PR 카드만 보여서 깔끔하고, 자세한 히스토리는 스레드에서 봐요.
  • 리뷰어는 디스코드 멘션으로 바로 알림을 받아요.

05 · PR 을 열면

카드 + 스레드가
생겨요

  • PR 템플릿의 🤖 Summary 를 읽어 작업 요약으로 보여줘요.
  • 본문의 close #12 를 찾아 연관 이슈와 열림/닫힘 상태를 붙여요.
  • 팀원 전원을 스레드에 초대해 사이드바에 바로 떠요.
  • draft PR 은 조용히 기다렸다가 Ready for review 때 올려요.

09 · 핵심 구현 ①

"아까 그 스레드" 를 어떻게 기억할까?

GitHub Actions 는 실행이 끝나면 아무것도 기억하지 못해요. 그런데 커밋 알림은 처음 만든 그 스레드로 가야 해요.

→ 처음 카드를 만들 때 디스코드 메시지/스레드 id 를 PR 댓글에 숨겨서 저장해요. 다음 이벤트는 이 댓글을 읽어서 같은 곳을 찾아가요.

DB 나 서버 없이 PR 자체가 저장소가 되는 셈이에요.

10 · 핵심 구현 ②

웹훅이 아니라 봇을 쓴 이유

웹훅 (Webhook)봇 (Bot Token)
메시지 보내기가능가능
메시지에서 스레드 만들기어려움가능
팀원을 스레드에 초대불가가능
설정 난이도URL 하나봇 생성 + 서버 초대

"PR 하나 = 스레드 하나" 구조를 만들려면 스레드 생성이 꼭 필요해서 봇 토큰 + Discord REST API 를 선택했어요.

11 · 핵심 구현 ③

신경 쓴 디테일

🚦

중복 스레드 방지

PR 을 열면서 리뷰어를 지정하면 이벤트 2개가 동시에 와요. PR 별 concurrency 로 줄 세워서 처리해요.

🛡️

인젝션 방지

PR 제목에 $(rm -rf) 같은 게 들어와도 실행되지 않게, 사용자 입력은 jq 로만 읽어요.

✂️

길이 제한

디스코드 메시지는 2000자 제한이 있어서, 긴 PR 본문도 잘라서 안전하게 보내요.

12 · 우리 프로젝트에 적용하기

합세 · 앱잼에서 3단계면 끝

1

디스코드 봇 만들고 서버에 초대

Developer Portal 에서 봇 생성 → 토큰 복사 → 초대 링크로 서버에 추가

2

파일 2개 복사

.github/workflows/discord-pr-bot.yml · .github/scripts/discord-pr-bot.sh

3

Secrets 3개 등록

DISCORD_BOT_TOKEN · DISCORD_PR_CHANNEL_ID · DISCORD_USER_MAP

자세한 방법은 docs/discord-pr-bot.md 에 정리해뒀어요.

13 · 회고

어려웠던 점

  • 상태를 어디에 저장할까 — Actions 는 매번 새로 시작해서, PR 댓글을 저장소처럼 쓰는 방법을 찾았어요.
  • 웹훅의 한계 — 처음엔 웹훅으로 충분할 줄 알았는데, 스레드를 만들려면 봇이 필요했어요.
  • 이벤트 순서 — opened 와 review_requested 가 거의 동시에 와서 스레드가 2개 생길 수 있었어요.
